# 灾害数据库模块技术思路

> 所属系统：青藏高原冰冻圈灾害数字孪生系统
> 对应后端：`disaster.py`、`data_query.py`、`basin.py`；数据：`data/raw/geo/*` 灾害点图层、ERA5 气象水文栅格及 `TibetanPlateau_index.db` 索引
> 文档性质：模块级技术思路（定位、技术路线、核心方案、关键设计决策、接口关系）

---

## 1 模块定位与目标

灾害数据库模块是系统的**多源灾害时空数据底座**，负责集成、组织与提供青藏高原冰冻圈灾害的目录化数据服务。其目标是为灾害过程模拟、风险评估与决策支持等上层模块提供**统一、可检索、可溯源**的灾害本底数据与气象水文驱动数据，是"数据—模拟—评估—决策"链路的第一环。

模块覆盖**八类冰冻圈灾害**与**气象水文背景场**两大主题，强调"数据即资产"的管理理念，所有记录均来自公开权威资料或实测/再分析产品。

---

## 2 总体技术路线

```
八类灾害点图层 (GeoJSON)  ──┐
气象水文场 (ERA5 TIF) + SQLite 索引 ──┤
基础地理/流域边界 (GeoJSON)  ──┤
                                  ▼
        [后端：disaster.py 类型路由 · data_query.py 变量检索 · basin.py 图层]
                                  ▼
        [空间查询 + 属性检索 + 动态计数 + 统计汇总]
                                  ▼
        [JSON / GeoJSON 服务 → 前端地图叠加与属性浏览]
```

## 3 核心技术方案

### 3.1 八类灾害数据集成

灾害点数据以 GeoJSON 要素集形式组织，后端通过**类型白名单**映射至具体文件（`disaster.py: load_disaster_data`）：

| 灾害类型（接口标识） | 中文名 | 数据文件 |
| --- | --- | --- |
| `rainfall_floods` | 降雨型洪水（PFs） | `PFs_HMA.geojson` |
| `snowmelt_floods` | 融雪型洪水（SFs） | `SFs_HMA.geojson` |
| `glacial_lake_floods` | 冰湖溃决洪水（GLOFs） | `GLOFs_HMA.geojson` |
| `landslide_dam_floods` | 滑坡堰塞湖溃决洪水（LLOFs） | `LLOFs_HMA.geojson` |
| `glacier_surging` | 冰川跃动 | `surging_glacier_inventory_gamdam_v2.geojson` |
| `rts_qtp` | 热融滑塌（RTS） | `RTS-QTP.geojson` |
| `blizzard_hazard` | 风吹雪危害 | `风吹雪危害范围.geojson` |
| `avalanche_hazard` | 雪崩危害 | `雪崩危害范围.geojson` |

每类灾害对应一套统一的接口契约：`GET /api/disaster/<type>` 返回该类型全部要素（保留原始坐标与属性），`GET /api/disaster/types` 返回全部类型元信息并**动态统计各类型要素数量**（文件缺失时计数为 0，不报错），便于前端构建灾害目录与数量概览。

### 3.2 空间查询与检索

- **类型路由**：以路径参数 `<disaster_type>` 区分灾害类别，配合白名单校验防止非法类型探测。
- **要素级返回**：后端以 `json.dumps(..., ensure_ascii=False)` 直接序列化，避免坐标被误转为字符串，保证前端几何解析正确。
- **健壮性**：文件不存在或解析失败时返回结构化错误（404/500），缺字段时降级报错，不影响其他类型可用性。

### 3.3 气象水文数据查询

气象水文背景场（ERA5 气温、降水等）由 `data_query.py` 提供服务：

- `GET /api/query/variables`：列出可用变量（如 `temperature_2m`、`total_precipitation_sum` 及其最大值变体）；
- `GET /api/query/list`：按日期范围检索指定变量的栅格文件路径与属性；
- `GET /tif/<path>`：下发具体 TIF 文件供前端/计算模块读取；
- **索引加速**：栅格文件通过 `data/processed/db/TibetanPlateau_index.db`（SQLite）建立"变量—日期—文件路径"索引，避免目录遍历，提升检索效率（亦被灾害过程模拟模块复用）。

### 3.4 属性浏览与统计

前端（查询页 `query.html` 及首页图层）对返回的灾害点做属性表格浏览、按字段筛选与空间分布统计；八类灾害的数量统计直接驱动首页与研究区概况面板。

## 4 关键设计决策

1. **文件即数据、类型白名单路由**：灾害点以独立 GeoJSON 文件存储，后端用枚举式白名单映射类型→文件，结构简单、易扩展（新增灾害类型只需增文件+加映射），同时封堵路径遍历风险。
2. **动态计数而非静态配置**：`/api/disaster/types` 实时读取文件统计要素数，缺失数据自动归零，使前端目录与数据实际状态始终保持一致，避免"目录有、数据无"的失真。
3. **SQLite 索引隔离大文件检索**：ERA5 栅格数量大，直接目录扫描昂贵；以轻量 SQLite 索引承载"变量—日期—路径"关系，被数据库查询与径流模拟共同复用，是模块间共享的关键数据契约。
4. **GeoJSON 直读 + 进程缓存**：`load_json_cached` 对解析后的 JSON 做内存缓存，避免重复 I/O；代价是多进程部署时各进程独立缓存、内存略增。

## 5 模块间接口关系

**上游依赖**
- `basin.py` 提供流域/行政边界，作为灾害点空间关联的参照与下游空间裁剪基准；
- `data/raw/geo/*` 原始矢量与 `TibetanPlateau_index.db` 为数据的物理来源。

**下游服务**
- **灾害过程模拟**：融雪洪水识别（snowmelt_flood）依赖 GLDAS 融雪数据，降雨/融雪洪水类型与模拟结果在地图上对照校验；
- **风险评估**：GLOFs、SFs、PFs、LLOFs 等灾害类型与风险等级图层共同呈现，支撑"灾害本底—风险格局"对照；
- **决策支持**：决策内容库（防灾实例）与灾害类型一一对应，专家咨询与智能体据此引用真实灾害记录；
- **首页**：八类灾害计数与分布直接驱动综合展示与图层叠加。

---

## 6 输入/输出与数据约定

- **输入**：八类灾害 GeoJSON（含几何与属性）、ERA5 气象水文 TIF 及其 SQLite 索引、基础地理图层。
- **输出**：类型化灾害要素集（GeoJSON）、类型目录与计数（JSON）、变量列表与栅格路径（JSON/TIF）。
- **数据约定**：灾害点 `properties` 须含可展示属性字段；坐标统一 WGS84；文件缺失时接口须返回计数 0 而非异常中断。

---

## 7 已知边界与后续规划

- **属性深度**：当前以"点/面分布 + 基础属性"为主，后续可补充灾害事件的时序（发生年、演进过程）、损失量级与文献出处链接，提升可溯源性。
- **历史灾情校验样本**：文档《数据需求与缺口对照》指出环境缺历史山洪/冰湖溃决点用于模型 ROC 校验，建议在灾害库中单列"历史灾情事件"子类，支撑模拟与分级验证。
- **索引一致性**：SQLite 索引须与 TIF 文件同步更新，规划由数据管理模块在上传时自动重建索引，避免"有文件无索引"。
- **空间关联**：可建立灾害点→所属流域/县域的自动挂接，支撑按行政单元的灾害频次统计。
