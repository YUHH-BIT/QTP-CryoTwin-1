# 07 三维示范区建设方案（v4 · Three.js 引擎）

> **一句话**：把雅鲁藏布江流域的真实海拔数据下载下来，做成一个可以旋转、可以缩放的**立体地形模型**，
> 表面贴上卫星照片，用 **Three.js 引擎**在网页里显示出来。

> **决策演进**：v1（MapLibre）→ v2（Cesium + 全域瓦片，格式层验证通过但工程复杂度高）
> → v3（喜马拉雅矩形试验区）→ **v4（当前：雅鲁藏布江流域 + 按边界裁剪）**。
> 状态：**已落地并在真实浏览器验证**（无头 Edge 截图 + DOM 探测，见 §8）。

---

## 0. 先讲人话：它到底是什么

### 0.1 它是三维的，不是卫星地图

| | 二维卫星地图（首页那个） | 三维示范区 |
| --- | --- | --- |
| 数据 | 只有颜色：每个像素一个 RGB | 颜色 **+** 高度：每个顶点一个海拔 |
| 视角 | 只能平移缩放，永远是俯视 | 可旋转到侧面，**看得见山脊的侧影和天空** |
| 垂直夸张滑杆 | 没有（平的东西没法夸张） | 有，0.5×–3×，山会真的长高 |
| 流域边界 | 画在平面上的线 | 贴在起伏地形上，侧看是悬在半空的 |

**表面那张图确实是卫星影像**（Esri World Imagery），所以它"看起来像"卫星地图；
但底下垫着 49 万个真实高程点，是立体的。

一句话：**它是"贴了卫星照片的三维地形模型"，不是一张照片。**
油漆刷在雕塑上，换成灰色漆，雕塑还是雕塑。

### 0.2 "瓦片"只是搬数据的纸箱

瓦片 = 把一整张超大的地图切成很多 256×256 的小方块，按需取用（所有在线地图都这么干）。

**但瓦片只出现在"做数据"那一步**：脚本下载 690 块高程瓦片、690 块影像瓦片，
在**本地拼成两张完整大图**，之后瓦片就扔掉了。
页面加载时拿到的是**一整块网格 + 两张整图**，不是一个瓦片服务。

所以运行时**零瓦片**——这也是它比旧方案快、稳的原因。

### 0.3 "贴图"是什么

先用高程数据捏出一个**灰白色的立体模型**（这时它已经有高度了，但表面没颜色），
再拿一张图"糊"在表面上——那张图就叫贴图。

- **几何** = 高度，决定山有多高（这是"三维"的来源，永远不变）
- **贴图** = 表面颜色，决定看起来是带雪的还是灰白的

按钮切的就是"表面糊哪张图"，切完山的高度一点没变。

## 1. 引擎：Three.js

| 项 | 内容 |
| --- | --- |
| 是什么 | 一个在网页里画三维图形的 JavaScript 库（开源，MIT） |
| 版本 | r160 |
| 存放 | `webgis_frontend/js/lib/three.module.js` + `OrbitControls.js`（**本地托管，不连 CDN**） |
| 干什么 | 把 49 万个带高度的顶点连成面、贴上贴图、打上光、让你能用鼠标转动 |
| 不干什么 | **不负责造山**。高度是真实数据给的，换任何引擎山都一样 |

**为什么不用 importmap**：importmap 一旦没生效，整个模块会**静默不执行**（页面卡在"正在加载"且不报错，
排查极痛苦）。改成相对路径 `./js/lib/three.module.js` 直接导入，并把所有错误可视化到画面中央。

**相机控制**：`OrbitControls`——左键转、滚轮缩放、右键平移；自动旋转默认开（速度 0.55）。

## 2. 整体流程：两段，中间只靠 5 个文件

```
【离线生成】scripts/build_terrain_page.py（一条命令，约 4 分钟）
     ① 读流域多边形 → ② 下载高程 + 影像 → ③ 插值成网格 → ④ 输出 5 个文件
                              ↓
【交给浏览器】webgis_frontend/terrain3d/yarlung/
     height.bin  mask.bin  texture.jpg  texture_hillshade.jpg  meta.json
                              ↓
【浏览器渲染】terrain3d.html + Three.js 引擎
     读文件 → 建几何体（填 Y = 高度）→ 只画流域内的三角形 → 贴图 → 打光 → 可交互
```

### 2.1 产物清单（实测共 **4.4 MB**）

| 文件 | 内容 | 实测大小 |
| --- | --- | --- |
| `height.bin` | 701×701 个高程值（int16，存相对最低点的差值） | 982,802 B（= 701²×2，精确匹配） |
| `mask.bin` | 701×701 掩膜（1=流域内，0=流域外） | 490,000 B |
| `texture.jpg` | 卫星影像贴图 | 1.87 MB |
| `texture_hillshade.jpg` | 地形明暗图（本地由高程算出） | 1.05 MB |
| `meta.json` | 范围、尺寸、高程极值、流域面积、边界折线 | 60 KB |

## 3. 高度是怎么来的（核心）

### 3.1 数据源

| 项 | 内容 |
| --- | --- |
| 数据 | **Terrarium 高程瓦片**（AWS 开放数据，SRTM 派生，全球覆盖、无密钥） |
| 地址 | `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png` |
| 精度 | z10 层级 ≈ **152 m/像素** |
| 优点 | **服务端已填过洞**，无空洞、无伪影 |

**为什么不用项目自带的 DEM**：实测该 DEM 在喜马拉雅一带空洞率 **53.5%**
（27–26°N 整条带 100% 无数据，28–27°N 也有 84–100%）。强行填充会产生放射状楔形伪影——
这是旧方案"地形难看"的真正根因，换任何渲染器都救不了。换 Terrarium 后贴图干干净净。

### 3.2 四步把"数据"变成"高度"

| 步 | 做什么 | 说明 |
| --- | --- | --- |
| ① 下载 | 8 线程并发下载 690 块瓦片，缓存到磁盘 | 163 秒；重跑不再联网 |
| ② 解码 | `高程 = R×256 + G + B/256 − 32768` | 高程被编进了像素颜色，读像素套公式即可还原 |
| ③ 采样 | 701×701 个经纬度点，双线性插值取值 | 得到 49 万个高程数字，第 0 行在最北 |
| ④ 填进 Y | `y = minHeight + 高差 × 夸张` | **这一步做完，山就立起来了** |

存盘时存的是**相对最低点的差值**（int16，体积减半），基准高度 `minHeight` 放在 `meta.json` 里，前端加回去。

### 3.3 精度上要诚实说一句

网格是 **2.2 km 一个顶点**（1533 km ÷ 700），而源数据是 152 m/像素——约 14×14 个源像素被压成一个点。
**尖锐峰顶必然被削平**：喜马拉雅试验区实测珠峰网格值 8641 m，官方 8849 m，差 208 m。

这是分辨率的必然代价，不是 bug。想更准：`--mesh 1200`（顶点数翻 3 倍，浏览器吃力）或缩小范围。

## 5. 按流域边界裁剪

用户要的是"流域"，不是矩形。做法：

1. `geopandas` 读 `data/raw/geo/TP_basins.geojson`，按名字匹配「雅鲁藏布江」，
   `unary_union` 合并后取 `bounds` → 外接矩形；
2. 用 `rasterio.features.rasterize` 把流域多边形栅格化成 701×701 的 `mask.bin`；
3. 前端建三角形索引时 `if (mask[i] === 0) continue`——**不是删顶点，是不给流域外的格子建三角形**。
   顶点还在，但不参与渲染，简单且不会破坏网格连续性。

| 项 | 实测 |
| --- | --- |
| 流域面积 | **34.9 万 km²** |
| 外接矩形 | 82.02–97.77°E / 26.96–31.28°N（1533×477 km） |
| 实际渲染 | 流域内 **235,704 个四边形**（占外接矩形 48%） |
| 边界线 | 黄色折线，用边界经纬度反查网格高程，Y = 该点高程 + 800 m；夸张变化时同步更新 |

## 7. 运维手册

```bash
# 生成雅鲁藏布江流域（当前这一版）
python scripts/build_terrain_page.py --basin 雅鲁藏布江 --region-id yarlung --zoom 10 --mesh 700

# 换流域（项目流域数据里任选：恒河、印度河…）
python scripts/build_terrain_page.py --basin 恒河 --region-id ganga --zoom 10 --mesh 700

# 自定义矩形范围
python scripts/build_terrain_page.py --bbox 85,28,90,30.5 --region-id custom1 --zoom 11

# 更精细（瓦片数约 4 倍，生成约 15 分钟）
python scripts/build_terrain_page.py --basin 雅鲁藏布江 --region-id yarlung --zoom 11 --mesh 900

# 不裁剪（保留整块矩形 + 边界线）
python scripts/build_terrain_page.py --basin 雅鲁藏布江 --region-id yarlung --no-clip
```

| 参数 | 含义 | 默认 |
| --- | --- | --- |
| `--basin` | 按项目流域数据做（自动取边界与名称） | — |
| `--bbox` / `--place` | 自定义矩形 / 预设区域 | himalaya |
| `--region-id` | 输出目录名（页面用 `?region=` 访问） | 与 basin/place 同名 |
| `--zoom` | 瓦片层级（10≈152 m/px，11≈77 m/px） | 11 |
| `--mesh` | 网格边数（701 = 701×701 顶点） | 600 |
| `--texture` | 贴图长边像素 | 4096 |
| `--jobs` | 下载并发数 | 8 |
| `--no-clip` / `--no-imagery` | 不裁剪 / 不下载影像（只出地形明暗图） | — |

**环境**：脚本用项目内嵌运行时（`.runtime/python/python.exe`），
rasterio / numpy / geopandas / PIL 均已具备，**零新增依赖**。瓦片缓存在
`data/processed/3d/tile_cache/`，重跑同一区域不会重复联网。

## 9. 已知限制（如实标注）

1. **峰顶被削平**：2.2 km 网格对尖锐峰顶必然低估（珠峰 -208 m）。
2. **Esri 影像需联网一次**（生成时下载）；之后完全离线。地形明暗图始终离线可用。
3. **Esri World Imagery 有署名要求**——页面左下角已标注。
4. **珠峰在雅鲁藏布江流域外**（流域南界是喜马拉雅主脊），所以这块地形不含珠峰主峰。
   需要珠峰请用恒河流域，或改用喜马拉雅矩形区（`?region=himalaya`）。
5. **无 LOD、无瓦片服务**：放大到很近时不会自动加载更精细的数据。这是简化版的有意取舍。

## 10. 已叠加的业务图层

数据全部来自 `data/raw/geo/`（与二维地图同源），由 `scripts/build_terrain_page.py`
按流域边界裁剪后随地形一起输出，运行时只读本地文件，不再查库。

| 图层 | 数据源 | 渲染方式 | 流域内数量 |
| --- | --- | --- | --- |
| 冰川 | `cryosphere/TP_China_glaciers.geojson` | 700×700 栅格掩膜 → 逐格贴地小面 | 14952 个 / 11081 km² |
| 冰湖 | `hydrology/TP_China_Lake.geojson` | 矢量多边形三角化贴地 | 2 个 |
| 河流 | `hydrology/river.geojson`（HydroRIVERS） | 线段批量贴地，按斯特拉勒级别分主干/支流 | 2244 段 / 6050 km |
| 灾害点 | `disaster/GLOFs_HMA`、`LLOFs_HMA`、`PFs_HMA`、`SFs_HMA` | 球体标记 + 类型配色 | 83 个（GLOF 56 / LLOF 5 / PF 15 / SF 7） |
| 冻土分布 | `models/Perma_Distr_map21/Perma_Distr_map21.tif` | 冻土图栅格重投影到地形网格，按类别着色（2×2 并格） | 多年冻土 8.73 万 km² / 季节性冻土 20.57 万 km² |
| 危害范围 | `disaster/` 下雪崩、风吹雪、RTS | 半透明多边形贴地 | 2 / 1 / 0 |

**河流图层要点**：HydroRIVERS 本身不含名称，导出时用国家级 1:400 万水系
（`TP_China_rivers.geojson`）对主干河段（级别 ≥ 6）做最近距离匹配补中文名，
阈值 2 km，2244 段中 583 段拿到名称（如雅鲁藏布江）。
线宽受 WebGL 限制恒为 1 px，因此用高对比青色（主干 `#00d5ff`、支流 `#7fe3ff`）
并抬到冰川之上（+110 m）保证可辨。

**冻土图层要点**：数据源是青藏高原冻土分布图栅格（Albers 等积投影 ESRI:102025，
937.49 m 像元），`gridcode` 为 0/1/2 三类。因原始数据无分类说明，用**面积与高程双重校验**
判定语义（结果与文献高度吻合）：

| 取值 | 判读 | 全高原像元 | 面积 | 高程中位 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 1 | 多年冻土 | 1,200,796 | 105.5 万 km² | 5256 m | 文献多年冻土 1.06×10⁶ km² |
| 0 | 季节性冻土 | 1,572,262 | 138.2 万 km² | 4747 m | 文献季节性冻土 1.46×10⁶ km² |
| 2 | 非冻土 | 33,177 | 2.9 万 km² | 2038 m | 藏南低海拔谷地，不纳入冻土要素 |

导出时用 `rasterio.warp.reproject`（最近邻）把栅格重采样到地形的 700×700 网格，
再与流域掩膜求交，得到 `permafrost.bin`（490 KB）。前端按类别生成贴地面，
**2×2 合并成一格**（多年冻土 17,095 格、季节性冻土 36,807 格）——原始 19.7 万格全部独立成面
会产生近 120 万顶点，并格后降到约 32 万，观感无损、帧率可控。
冻土面用不受光照的 `MeshBasicMaterial`，否则光照会让大片色块发灰、与影像混在一起。

点击任意要素弹出属性卡：冰川给面积/高程，河流给级别/河段长/年均流量，
冻土给类别/海拔/流域内面积，灾害点给时间/成因/伤亡等原始字段。

## 11. 与旧方案（Cesium 全域）的关系

v2 的 Cesium 方案**磁盘上仍完整保留**，随时可切回：

| 内容 | 位置 |
| --- | --- |
| 生成脚本 | `scripts/build_3d_tiles.py` |
| 后端蓝图 | `webgis_backend/modules/scene3d.py` |
| 全域瓦片 | `data/processed/3d/tp_full/`（18.7 万片 / 3.73 GB） |
| 前端 | `webgis_frontend/js/scene3d.js` + `webgis_frontend/cesium/` |
| 测试 | `tests/test_scene3d.py` |

**为什么当时放弃**：全域 z0–z12 要 18.7 万片瓦片，还要配瓦片服务、LOD、接缝处理，
任一个环节出问题就"看起来不像三维"，而排查手段有限。
单块网格把变量收敛到"一个网格 + 一张贴图"，几分钟就能确认对不对。

需要时把 `decision.html` 的入口换回 `?cat=scene3d` 即可。
